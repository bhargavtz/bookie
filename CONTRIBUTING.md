# Contributing to Bookie

Bookie is a rights-controlled digital library. Contributions are welcome if they keep its rules intact. Read [CODING_STANDARDS.md](CODING_STANDARDS.md), [docs/architecture.md](docs/architecture.md) and [docs/wiki/index.md](docs/wiki/index.md) first; [AGENTS.md](AGENTS.md) lists commands and stage ownership.

## Before you start

1. Check existing issues and pull requests. For larger changes open an issue first.
2. Do not commit credentials, `.env*` files (only `.env.example`, with placeholders), private content, build output or `node_modules`.
3. **Do not add books, covers, PDFs, images or text you do not own or have a recorded licence for.** No fake books, licences, ISBNs or statistics, including in seeds and fixtures. Test PDFs are generated by the repo (`npm run gen:pdfs`). Every shipped asset needs a provenance entry in [docs/ASSETS.md](docs/ASSETS.md).

## Local development

Node `>=22.13`, then `npm ci` (not `npm install`). See [docs/setup.md](docs/setup.md).

```bash
npm ci
cp .env.example .env.local
npm run db:setup
npm run dev
```

Before opening a pull request:

```bash
npm run verify    # env check, eslint, typecheck, unit + integration tests
npm run build     # separate; slow
```

Run `npm run e2e` when you change user-visible behaviour (needs a build and `npx playwright install chromium`). Details: [docs/testing.md](docs/testing.md).

## Rules reviewers enforce (summary)

- Access to any book or file goes through `src/lib/policy`; never write an ad-hoc `status === "published"` check.
- Layering: pages and route handlers call services; services call repositories; only repositories touch tables.
- Validate every boundary with zod; read environment only through `getEnv()`; never log or return env values.
- Schema changes: edit the Drizzle schema, run `npm run db:generate`, commit the SQL. Never edit a committed migration; no destructive migration without review ([docs/database.md](docs/database.md)).
- A bug fix lands with a test that fails without it. Keep 100% branch coverage on `src/lib/policy/index.ts`.
- Accessibility: semantic landmarks, visible focus, labelled controls, reduced-motion support.
- New decisions get a dated wiki page and an entry in `docs/wiki/index.md`; wiki claims carry a date and a commit reference.

## Pull requests

- Use a focused branch such as `feat/admin-rights-filter` or `fix/range-header`.
- Explain what changed and why, and link the issue.
- Include screenshots or a short recording for visual changes, and call out accessibility, responsive and performance considerations.
- Keep unrelated formatting changes out.
- Dependency changes need a justification; risky libraries are pinned exactly.

## Commits and review

Use clear imperative commit messages. Reviewers check behaviour, TypeScript correctness, rights and security rules, tests, accessibility, and that no secrets or generated files were added.
